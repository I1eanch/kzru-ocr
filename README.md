# kzru-ocr — локальный OCR PDF-сканов RU/KK

Офлайн-модуль: PDF-скан на входе, дословный UTF-8 текст в правильном порядке
чтения на выходе. Никаких внешних API. Только CPU.

Рассчитан на печатные документы РК — уставы, договоры, справки, письма,
бизнес-планы: сплошной текст, машинный шрифт, простые таблицы, печать и
подпись внизу.

## Чем это отличается от вызова облачной модели

Ставка сделана не на «более умную модель», а на **самопроверяемый вывод**.
Контрольный разряд БИН/ИИН, сверка суммы цифрами и прописью, календарная
валидация даты — это детерминированные проверки, которых мультимодальная LLM
не делает. Поэтому сервис не только отдаёт текст, но и сообщает, где ему не
следует доверять:

| warning | когда возникает |
|---|---|
| `bin_checksum_failed` | 12-значный номер не проходит контрольную сумму и не исправим |
| `bin_repaired` | номер исправлен по контрольной сумме — **проверьте оригинал** |
| `bin_ambiguous_fix` | исправлений несколько, ни одно не выбрано |
| `amount_mismatch` | сумма цифрами не совпадает с суммой прописью |
| `date_invalid` | несуществующая дата |
| `low_confidence_page` | средняя уверенность страницы ниже 0.70 |
| `engine_disagreement` | движки разошлись в цифрах (профиль `accurate`) |
| `text_layer_rejected` | текстовый слой признан негодным, страница ушла в OCR |
| `page_failed` | страница не обработана |

Правило по БИН/ИИН согласовано с владельцем: **исправлять только если валидный
кандидат ровно один**; при нескольких — не исправлять и поднять
`bin_ambiguous_fix`. Любое исправление видимо через `bin_repaired`.

## Установка

Всё работает в одном образе, host-зависимостей кроме Docker нет.

```bash
docker build --target runtime -t kzru-ocr:dev -f docker/Dockerfile .
docker run --rm kzru-ocr:dev sh -c 'tesseract --version; tesseract --list-langs'
```

Образ содержит Tesseract 5.3 и `tessdata_best` для `rus`, `kaz`, `osd`
(Apache-2.0), плюс `tessdata_fast` из Debian для профиля `fast`.

Опциональный таргет `full` добавляет PaddleOCR. PyPI отдаёт `paddlepaddle`
только для manylinux x86_64, поэтому он собирается на amd64-хосте:

```bash
docker build --platform linux/amd64 --target full -t kzru-ocr:full -f docker/Dockerfile .
```

Проверка доменного слоя (контрольная сумма БИН/ИИН, числительные, даты,
гомоглифы) — 62 кейса, включая известное слепое пятно 11-й позиции:

```bash
docker run --rm kzru-ocr:dev python tests_domain.py
```

## Запуск

CLI (образ самодостаточен; монтирование нужно лишь чтобы отдать ему свои PDF
и забрать результат):

```bash
docker run --rm -v "$PWD":/app -w /app -e PYTHONPATH=/app kzru-ocr:dev \
  python -m ocr.cli scan.pdf --profile balanced --render default

docker run --rm -v "$PWD":/app -w /app -e PYTHONPATH=/app kzru-ocr:dev \
  python -m ocr.cli --in-dir bench/scans --out-dir out --json report.json
```

HTTP-сервис (именно так его вызывает PHP — модели остаются в памяти):

```bash
docker run --rm -p 8099:8099 kzru-ocr:dev
curl -s localhost:8099/healthz
curl -s -F file=@scan.pdf 'localhost:8099/ocr?profile=balanced' | jq .text
```

Асинхронный режим для больших документов: `POST /jobs` → `202 {job_id}`,
затем `GET /jobs/{job_id}`.

Из CodeIgniter 4 — через `php/OcrClient.php`:

```php
$client = new \App\Libraries\OcrClient();       // OCR_SERVICE_URL или 127.0.0.1:8099
$result = $client->recognize($pathToPdf, 'balanced');
$text   = $result['text'];
foreach ($result['warnings'] as $w) { /* $w['type'], $w['page'], $w['detail'] */ }
```

## Профили

Допустимое время на документ заказчиком пока не названо, поэтому бюджет
закрывается выбором профиля, а не переписыванием пайплайна.

| Профиль | Состав | CER norm | digit CER | с/стр |
|---|---|---|---|---|
| `fast` | `tessdata_fast`, psm 6, 250 DPI, без OSD/deskew/Sauvola | 0.0416 | — | ~1.9 |
| `balanced` | `tessdata_fast`, psm 6, 300 DPI, OSD + deskew + Sauvola + проход по цифрам | **0.0366** | 0.0125 | ~2.5 |
| `accurate` | то же при psm 4 и 400 DPI | 0.0386 | **0.0121** | ~3.5 |

`accurate` сознательно хуже по общему CER и лучше по цифрам: критерий приёмки
требует безошибочных БИН, сумм и дат, а не минимального CER.

### Масштабирование по страницам

Замер на VPS (4 ядра, x86_64, Debian, `bench/measure_parallel.py`), документ
из 8 страниц, профиль `balanced`:

| workers | итого | с/стр | ускорение |
|---|---|---|---|
| 1 | 20.4 с | 2.55 | 1.00x |
| 2 | 12.6 с | 1.57 | 1.62x |
| 4 | 9.3 с | 1.17 | 2.19x |

Экстраполяция на 30 страниц при 4 ядрах — около 35 с. Ускорение ниже
линейного закономерно: в параллельном режиме каждый воркер однопоточный, а
одиночный Tesseract сам занимает около 3.3 ядер.

Путь к этим числам стоит описать, потому что две ловушки здесь неочевидны и
обе давали замедление вместо ускорения:

1. **`tesseract` игнорирует `OMP_NUM_THREADS`.** Замер одной страницы A4:
   wall 1.64 с при 5.43 с CPU, то есть 3.3 потока. Ограничивает его только
   `OMP_THREAD_LIMIT=1` (wall 1.99 с при 1.97 с CPU, текст побайтово тот же).
   Без этого N воркеров требуют 3.3·N ядер.
2. **`fork` + пул потоков OpenCV = зависание.** Родитель к моменту форка уже
   работал с OpenCV, и воркеры не завершались минутами при 20 с на одном.
   Пул создаётся с `mp_context="spawn"`, профиль передаётся объектом, а не
   именем через глобальный реестр.

Отдельно: `nproc` внутри контейнера показывает 1, потому что coreutils
уважает `OMP_NUM_THREADS`, выставленный в образе. Это не cgroup-лимит —
`sched_getaffinity` и `cpu.max` показывают все ядра. Число воркеров берётся из
`ocr.pipeline.available_cpus()`, которая читает affinity и cgroup-квоту
(v1 и v2), а не `nproc` и не `os.cpu_count()`.

Профили вывода (`--render`) задают конвенцию текста, а не распознавание:
`default`, `cells`, `pipe`, `space`, `joined`, `no-headers`, `flat`. Когда
придёт эталон заказчика, нужный профиль **подбирается прогоном решётки**
(`sh bench/grid.sh`), а не угадывается.

## Пайплайн

```
PDF
 ├─ страница с годным текстовым слоем ─────────────→ текст напрямую (~7 мс)
 └─ скан или негодный слой
      ├─ PyMuPDF: растеризация, адаптивный DPI под высоту строчных 30 px
      ├─ OSD: ориентация 0/90/180/270
      ├─ deskew проекционным профилем (двухпроходный поиск ±5°, шаг 0.05°)
      ├─ median 3×3 + Sauvola на интегральных изображениях
      ├─ Tesseract 5 rus+kaz → слова с bbox и confidence
      ├─ (accurate) PaddleOCR kk → арбитраж по строкам
      ├─ доуточняющий проход по числам: кроп ×3 + whitelist цифр
      ├─ рекурсивный XY-cut: порядок чтения, колонки, таблицы
      └─ домен: гомоглифы, БИН, суммы, даты → warnings
```

Ключевые решения и почему именно так:

- **Текстовый слой проверяется, а не берётся на веру.** Часть входящих
  «сканов» несёт чужой плохой OCR-слой. Отвергается слой без кириллицы, с
  долей алфавитных символов ниже 0.45, с более 35% однобуквенных токенов и
  короткий текст на странице, закрытой изображением более чем на 70%.
- **Адаптивный DPI.** Tesseract LSTM чувствителен к масштабу; целевая высота
  строчных 30 px достигается ресайзом после растеризации.
- **Deskew проекционным профилем, не `minAreaRect`.** На странице с малым
  количеством текста, рамкой или печатью `minAreaRect` даёт угол по мусорному
  объекту. Проекционный профиль на разреженной странице возвращает 0.
- **`medianBlur` вместо `fastNlMeansDenoising`.** NL-means стоит 0.5–2 с на
  страницу на CPU — вне бюджета.
- **PaddleOCR — только PP-OCRv5.** Словарь `ppocrv5_cyrillic_dict.txt`
  содержит `Ә Ғ Қ Ң Ө Ұ Ү Һ І`; устаревший `cyrillic_dict.txt` (v3) их не
  содержит, и на v3 казахский физически нераспознаваем. Детектор запускается с
  `text_det_limit_side_len=2000`: дефолтные 960 px ужимают A4/300 DPI и
  уничтожают мелкий текст.
- **Цифры и буквы арбитрируются по-разному.** Слово можно выбрать по
  уверенности; цифру — нет. Расхождение движков в токене с цифрами не решается
  «по уверенности», а поднимается как `engine_disagreement`.
- **XY-cut вместо допущения «одна колонка».** Число колонок во входящих
  документах не гарантировано. Строки, пересекающие межколоночные коридоры,
  трактуются как готовые ряды таблицы; не пересекающие — как колонки, из
  которых ряды сшиваются по вертикальному перекрытию.

## Бенчмарк

```bash
# синтетический dev-набор: текстослойные PDF → псевдосканы + эталон
python -m bench.make_sample_docs --out-dir bench/data --count 8 --seed 42
python -m bench.make_pseudoscan --src-dir bench/data --out-dir bench/scans \
       --gt-dir bench/gt --dpi 200 --degrade medium --seed 42

python -m ocr.cli --in-dir bench/scans --out-dir bench/pred --profile balanced
python -m bench.run_bench --pred-dir bench/pred --gt-dir bench/gt \
       --csv report.csv --worst 10
```

`run_bench` печатает CER/WER в двух режимах — `strict` и `normalized` (NFC,
схлопывание пробелов, унификация тире и кавычек, нижний регистр) — потому что
конвенция подсчёта у заказчика пока не зафиксирована, и подменять одну другой
нельзя. Агрегат считается и микро- (взвешенно по символам эталона), и
макро-усреднением: это разные числа.

Field-accuracy считается отдельным блоком по `bin`, `amounts`, `dates` теми же
экстракторами, что применяются к эталону и к гипотезе.

Псевдоскан — бесплатный точный эталон: текстослойный PDF растеризуется,
деградируется (JPEG, шум, blur, перекос) и собирается обратно в PDF без
текстового слоя, а эталоном служит исходный текстовый слой. Он не заменяет
реальные сканы — артефакты сканера он не воспроизводит.

### Результаты на синтетическом dev-наборе

8 документов (уставы, договоры, справки), 16 769 символов эталона, псевдосканы
200 DPI с деградацией `medium`, профиль `balanced`, решётка профилей вывода:

| render | CER strict | CER norm | WER strict | WER norm |
|---|---|---|---|---|
| `flat` | **0.0490** | 0.0404 | 0.2353 | 0.2319 |
| `cells` | 0.0543 | **0.0391** | 0.3092 | **0.2066** |
| `default` | 0.0555 | 0.0404 | 0.3092 | 0.2319 |
| `joined` | 0.0555 | 0.0404 | 0.3092 | 0.2319 |
| `pipe` | 0.0601 | 0.0450 | 0.3597 | 0.2572 |

Field-accuracy (одинакова во всех профилях вывода):

| поле | ожидалось | найдено | верно | exact |
|---|---|---|---|---|
| `bin` | 16 | 16 | 16 | 1.0000 |
| `amounts` | 7 | 7 | 7 | 1.0000 |
| `dates` | 8 | 8 | 8 | 1.0000 |

Читать это следует так: **разброс CER между профилями вывода (0.049–0.060)
сопоставим с разницей между движками**, поэтому сравнение с baseline без
согласованной конвенции сериализации бессмысленно. Field-accuracy 1.0
получена на синтетике с чистыми шрифтами и не переносится на реальные сканы
автоматически; ценность здесь в том, что контрольная сумма БИН отработала на
всех 16 номерах.

Известные источники остаточного CER на этом наборе: путаница `щ`→`ш`
(`настоящий` → `настояший`) и потеря казахских литер, стоящих изолированно в
перечислении (`қ, ң, ө, ұ` → `к, н, ©, у`) — в связном тексте те же литеры
распознаются верно. Оба случая — кандидаты на дообучение.

### Bake-off движков (amd64 VPS, 4 ядра)

```bash
python -m bench.bakeoff --scans bench/scans --gt bench/gt --render cells
python -m bench.bakeoff --scans bench/scans --gt bench/gt --only tesseract
```

8 документов, 13 страниц, `render=cells`, один процесс на конфигурацию:

| конфигурация | CER norm | digit CER | с/стр |
|---|---|---|---|
| `tess-fast-psm6-300dpi` | **0.0366** | 0.0125 | 2.46 |
| `tess-fast-psm4-300dpi` | 0.0377 | 0.0125 | 2.51 |
| `tess-fast-psm4-400dpi` | 0.0386 | **0.0121** | 3.46 |
| `tess-best-psm4-300dpi` | 0.0388 | 0.0151 | 2.66 |
| `tess-best-psm6-300dpi` | 0.0391 | 0.0151 | 2.71 |
| `paddle-kk-side1280` | 0.0389 | 0.0788 | 3.35 |
| `paddle-kk-side2000` | 0.0428 | 0.1153 | 5.57 |
| `paddle-kk-side2500` | 0.0429 | 0.1373 | 7.55 |
| `ensemble-tess+paddle` | 0.0505 | 0.0169 | 7.39 |

Три вывода, каждый против исходного ожидания:

1. **PaddleOCR непригоден для этой задачи, хотя по общему CER не уступает.**
   `paddle-kk-side1280` даёт 0.0389 против 0.0366 у Tesseract — практически
   паритет. Но на цифрах он ошибается в 6–11 раз чаще (0.0788–0.1373 против
   0.0121–0.0151). Для проверки госдокументов, где ошибка в БИН или сумме
   недопустима, общий CER — не та метрика, по которой принимают решение.
   Отдельно любопытно, что у Paddle digit-CER **растёт** с разрешением
   детектора: 0.0788 → 0.1153 → 0.1373 при 1280 → 2000 → 2500.
2. **Ансамбль вредит.** `ensemble-tess+paddle` — 0.0505, хуже каждого движка
   по отдельности, при вдвое большей стоимости. Арбитраж по уверенности не
   спасает, когда второй голос систематически слабее. Paddle выведен из
   дефолтных профилей во флаг `--engine paddle`.
3. **`tessdata_fast` обошёл `tessdata_best`** во всех четырёх парах psm×DPI и
   при этом быстрее. Ожидание было обратным. Оговорка: набор синтетический, с
   чистыми гарнитурами DejaVu; на реальных сканах проверку надо повторить —
   именно для этого существует `bench/bakeoff.py`.

Field-accuracy на VPS для профилей `balanced` и `accurate` — 1.0000 по всем
трём типам полей (`bin` 16/16, `amounts` 7/7, `dates` 8/8).

### Поведение на сильно деградированных сканах

Тот же генератор с `--degrade heavy` (перекос до ±2.5°, соль-перец, JPEG q35,
эрозия), 3 документа, профиль `balanced`:

| метрика | `medium` | `heavy` |
|---|---|---|
| CER norm | 0.0366 | 0.3846 |
| средняя уверенность | 0.93–0.95 | 0.50–0.58 |
| warnings на документ | 1–3 | 4–11 |
| `bin` precision / recall | 1.00 / 1.00 | 0.86 / 1.00 |
| `amounts` exact | 1.00 | 0.00 |
| `dates` exact | 1.00 | 0.33 |

Это граница применимости, и её стоит знать до сдачи: при CER 38% текст
непригоден для автоматического разбора. Важно другое — **система не выдаёт
мусор молча**: уверенность падает до 0.5, поднимается `low_confidence_page`, и
число warnings растёт втрое. Такой документ можно автоматически отправлять на
ручную проверку вместо того, чтобы пропускать неверные данные дальше.

Здесь же виден эффект фильтрации по контрольной сумме: до неё регекс на
`heavy` находил 13 «БИН» против 6 настоящих (precision 0.46), после —
7 против 6 (precision 0.86) при сохранённом recall 1.00. Один ложный номер
всё же проходит проверку: случайная 12-значная последовательность
удовлетворяет контрольному разряду примерно в одном случае из одиннадцати.

## Дообучение (опционально)

Дообучение Tesseract LSTM идёт на CPU и почти не требует человеческого
времени: генерация синтетики — минуты, подготовка и обучение — часы в фоне.

```bash
docker build -f docker/Dockerfile.train -t kzru-ocr:train .

docker run --rm -v "$PWD":/work -w /work kzru-ocr:train \
  python train/make_synth.py --out train/synth --count 8000 --seed 42

docker run --rm -v "$PWD":/work -w /work kzru-ocr:train \
  make -C /opt/tesstrain training -j"$(nproc)" \
    MODEL_NAME=kzru_doc START_MODEL=kaz \
    TESSDATA=/opt/tessdata_best DATA_DIR=/work/train/data \
    GROUND_TRUTH_DIR=/work/train/synth \
    MAX_ITERATIONS=10000 RATIO_TRAIN=0.95
```

Три места, на которых это ломается, и все молча:

- **`-j` обязателен.** Подготовка строит `.box` и `.lstmf` по одной строке на
  процесс: замерено около 40 строк в минуту в один поток против 230 при
  `-j4`. 30 000 строк в один поток — примерно 12 часов только на подготовку,
  поэтому в примере 8000 строк и параллельный `make`.
- **`configs/lstm.train` должен лежать рядом с моделями.** Без него
  `tesseract` печатает `read_params_file: Can't open lstm.train` и не создаёт
  ни одного `.lstmf`, при этом `make` продолжает работать как ни в чём не
  бывало. В `docker/Dockerfile.train` каталог копируется в
  `/opt/tessdata_best/configs` именно поэтому.
- **DAWG-словари идут только все втроём.** Указать один `WORDLIST_FILE` без
  `PUNC_FILE` и `NUMBERS_FILE` нельзя: сборка падает на
  `Must have non-empty puncs list to use language models!!` уже после часа
  подготовки. Либо задавайте все три, либо ни одного — в примере выше
  словари не подключены сознательно.

Фактический прогон на 4-ядерном VPS: 8000 строк, `START_MODEL=kaz`,
подготовка около 35 минут, далее обучение. BCER на обучающей выборке падал
с 4.97% до 2.78% к 1111-й итерации из 10 000.

Полученный `kzru_doc.traineddata` подключается копированием в
`/opt/tessdata_best` и заменой `lang` в `ocr/engines/tesseract.py`. Принимать
его следует **только по результатам замера** на dev-наборе: `bench/bakeoff.py`
сравнит его со stock-моделью на тех же документах.

## Известные ограничения

- Колонка таблицы может слиться с соседней, если значение в итоговой строке
  сдвинуто и разбивает межколоночный коридор. Текст при этом не теряется —
  страдает только расстановка разделителей ячеек.
- Удаление цветной печати не реализовано: на grayscale-входе цветовая
  сегментация невозможна, а цветная растеризация удваивает память.
  `ocr/preprocess.remove_stamp` оставлен явной точкой расширения.
- Профиль `accurate` работает на обычном образе `runtime`. Образ `full` нужен
  только для `--engine paddle`, и по результатам bake-off этот путь
  не рекомендуется для документов с критичными числами.
- `/jobs` хранит состояние в памяти процесса: перезапуск сервиса теряет
  незабранные результаты.
- Всё измерено на синтетическом наборе с гарнитурами DejaVu. На реальных
  сканах выводы (в том числе «`tessdata_fast` лучше `best`») подлежат
  перепроверке тем же `bench/bakeoff.py`.

## Roadmap

1. Дообучение на реальных строках (размеченные кропы дают больше, чем 10k
   синтетики).
2. PaddleOCR как детектор строк с распознаванием Tesseract по кропам —
   устойчивее на перекошенных сканах.
3. Таблицы по морфологии линий (детекция сетки) вместо коридоров.
4. Снятие цветной печати на цветной растеризации.

## Лицензии зависимостей

| компонент | лицензия | как используется |
|---|---|---|
| Tesseract 5 + `tessdata_best`/`tessdata_fast` | Apache-2.0 | основной движок |
| poppler-utils (`pdftoppm`, `pdftotext`, `pdfinfo`, `pdfimages`) | GPL-2 | растеризация и текстовый слой, **бэкенд по умолчанию** |
| OpenCV (headless) | Apache-2.0 | препроцессинг |
| PaddleOCR + PaddlePaddle | Apache-2.0 | опциональный движок в образе `full` |
| PyMuPDF | **AGPL-3.0** | опциональный бэкенд `--pdf-backend pymupdf`, в дефолтном пути не задействован |

Про poppler и AGPL. Изначально растеризация шла через PyMuPDF, но он не входит
в разрешённый ТЗ стек и распространяется под AGPL-3.0, что для закрытого
коммерческого сервиса означает либо раскрытие исходников, либо коммерческую
лицензию Artifex. Poppler-утилиты вызываются как внешние процессы, без
линковки, и после оптимизации (PGM вместо PNG, один `pdftotext` на документ)
оказались быстрее: 4.96 с против 5.54 с на двухстраничном документе, а
параллелизм вырос с 2.19x до 3.13x. PyMuPDF остаётся в зависимостях только
ради `bench/make_pseudoscan.py` и `bench/make_sample_docs.py` — генераторов
тестовых данных, которые в продукт не поставляются.

Surya сознательно не используется: это VLM на 650M параметров, её заявленная
скорость 5 стр/с относится к RTX 5090, а на CPU через llama.cpp страница
занимает десятки секунд.
