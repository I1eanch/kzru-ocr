# kzru-ocr — локальное распознавание PDF-сканов на русском и казахском

Модуль извлекает текст из PDF-сканов без текстового слоя. Работает полностью
офлайн на обычном сервере без видеокарты, вызывается из PHP по HTTP.

Рассчитан на печатные документы Республики Казахстан: уставы, договоры,
справки, письма, бизнес-планы. Сплошной текст, машинный шрифт, простые
таблицы, печать и подпись внизу страницы.

**Главное отличие от облачной модели:** сервис не только отдаёт текст, но и
сообщает, где ему нельзя доверять. Контрольная сумма БИН/ИИН, сверка суммы
цифрами и прописью, календарная проверка дат — детерминированные проверки,
которых мультимодальная LLM не делает. Документ с сомнительными полями
помечается автоматически и может уходить на ручную проверку, вместо того
чтобы молча пройти дальше с неверной цифрой.

## Возможности

| Возможность | Детали |
|---|---|
| Входные данные | PDF до 15 МБ, от 1 до 30 страниц |
| Языки | русский и казахский, в том числе в одном документе |
| Выход | plain text UTF-8, порядок чтения сверху вниз и слева направо |
| Таблицы | построчно, разделитель ячеек настраивается |
| Текстовый слой | если он есть и пригоден — берётся напрямую, без OCR (в ~350 раз быстрее) |
| Критичные поля | БИН/ИИН с проверкой контрольного разряда, суммы, даты |
| Качество входа | перекос, шум, сканы 150–300 DPI |
| Работа в сети | не требуется ни при установке после сборки образа, ни при работе |

### Что делается с критичными полями

> [!IMPORTANT]
> Модуль **не гарантирует** отсутствие ошибок в критичных полях. Он
> обнаруживает значительную их часть и помечает всё, что не подтверждено;
> решение по помеченным полям принимает оператор. Ниже перечислено, где
> именно проверка не срабатывает.

**БИН и ИИН проверяются контрольным разрядом.** 12-значный номер РК содержит
контрольную цифру, поэтому часть ошибок распознавания видна арифметически.
Если номер не сходится, перебираются типичные ошибки OCR (`0`↔`8`, `1`↔`7`,
`5`↔`6` и прочие). Правило: **номер исправляется только если валидный
кандидат ровно один**; при нескольких кандидатах номер не подменяется.

Чего эта проверка не ловит:

- **ошибку ровно в 11-й позиции** — её вес 11 ≡ 0 по модулю 11, на сумму она
  не влияет; зафиксировано отдельным кейсом в `tests_domain.py`;
- **случайную последовательность** — произвольные 12 цифр проходят проверку
  примерно в одном случае из одиннадцати;
- **две и более ошибки одновременно** — перебор рассчитан на одиночную.

Поэтому каждое значение возвращается со статусом (`valid`, `repaired`,
`unverified`), и даже `valid` означает лишь «контрольный разряд сошёлся», а не
«номер верен».

**Суммы сверяются с записью прописью.** В договорах и справках сумма обычно
продублирована: `500 000 (пятьсот тысяч) тенге`. Обе записи разбираются и
сравниваются, на русском и на казахском. Расхождение — предупреждение. Если
прописи рядом нет, сверять не с чем: `words_match` равно `null`, и такая сумма
ничем, кроме самого распознавания, не подтверждена.

**Даты проверяются календарём.** Распознаются форматы `dd.mm.yyyy`,
`yyyy-mm-dd`, `«12» января 2026 года`, `12 қаңтар 2026 жыл`. Несуществующая
дата вроде `31.02.2026` помечается и не попадает в подтверждённые значения.
Существующая, но неверно распознанная дата (`12.01.2026` вместо `13.01.2026`)
проверку проходит — календарь такой подмены не видит.

## Стек технологий

Всё из разрешённого списка, всё ставится на собственный хостинг, никаких
внешних API.

| Компонент | Версия | Лицензия | Где |
|---|---|---|---|
| Debian | 12 (bookworm) | — | базовый образ, закреплён по digest |
| Python | 3.12 | PSF | среда выполнения |
| **Tesseract** | 5.3.0 (LSTM, `--oem 1`) | Apache-2.0 | production: распознавание, языки `rus` + `kaz` |
| **poppler-utils** | 22.12 | GPL-2 | production: `pdftoppm` — растеризация, `pdftotext` — текстовый слой, `pdfinfo`, `pdfimages` |
| **OpenCV** (headless) | 5.0.0 | Apache-2.0 | production: препроцессинг |
| NumPy | 2.5.3 | BSD-3 | production: вычисления |
| FastAPI + uvicorn | 0.141 / 0.53 | MIT / BSD-3 | production: HTTP-сервис |
| pytesseract | 0.3.13 | Apache-2.0 | production: вызов Tesseract |
| RapidFuzz | 3.14 | MIT | production: сопоставление строк при арбитраже движков |
| jiwer | 4.0 | Apache-2.0 | **только dev-образ**: метрики бенчмарка |
| PyMuPDF | 1.28 | **AGPL-3.0** | **только dev-образ**: генерация тестовых данных |
| pytest, httpx | — | MIT / BSD-3 | только dev-образ: тесты |
| PaddleOCR | 3.x | Apache-2.0 | только образ `full`, по умолчанию выключен |

### Две заметки по лицензиям

**PyMuPDF под AGPL-3.0 в production-образ не входит.** Это не декларация о
намерениях, а свойство сборки: `PyMuPDF` объявлен в `requirements-dev.txt`, а
не в `requirements.txt`, каталог `bench/` в production-образ не копируется, и
`scripts/smoke.sh` проверяет отсутствие пакета и каталога в собранном образе —
проверка падает, если они там появятся. Растеризация в рабочем пути идёт через
`pdftoppm` из poppler: внешний процесс, без линковки. Флаг
`--pdf-backend pymupdf` в production-образе вернёт ошибку «бэкенд недоступен»,
а `/readyz` не перечислит его среди доступных.

Это инженерная констатация состава образа, а не юридическое заключение:
вопрос применимости AGPL к вашей поставке решает ваш юрист.

**PaddleOCR по умолчанию отключён.** По результатам сравнения он ошибается на
цифрах в 6–11 раз чаще Tesseract при сопоставимом общем качестве текста, что
для проверки документов неприемлемо. Доступен в образе `full` для
экспериментов; подробности в [инженерных записках](docs/ENGINEERING.md).

## Системные требования

### Минимальные

| Ресурс | Требование |
|---|---|
| ОС | любой Linux с Docker (проверено: Debian 12) |
| Архитектура | x86_64 или arm64 |
| CPU | 2 ядра |
| RAM | 1 ГБ на контейнер при одном рабочем процессе |
| Диск | 1.5 ГБ: образ 640 МБ + место под временные файлы |
| GPU | **не требуется** |
| Сеть | нужна только на время сборки образа |

### Рекомендуемые

| Ресурс | Требование |
|---|---|
| CPU | 4 ядра и больше — обработка страниц распараллеливается |
| RAM | 4 ГБ |
| Диск | 5 ГБ |

### Про память

Цифры замерены, а не оценены. Один рабочий процесс укладывается в 1 ГБ.
Четыре процесса на профиле `accurate` (400 DPI) **не помещаются в 1 ГБ** —
контейнер убивается по OOM; при 1.5 ГБ работают стабильно. Практическое
правило: **512 МБ на рабочий процесс плюс 512 МБ базовых**.

Если памяти меньше — ограничьте число процессов параметром `workers`, а не
надейтесь на своп: пиковое потребление приходится на растеризацию страницы.

### Про ядра

Число рабочих процессов по умолчанию определяется автоматически из ядер,
реально доступных процессу (учитываются и affinity, и cgroup-лимит
контейнера). Если вы запускаете контейнер с `--cpus=2`, модуль это увидит и
не станет плодить лишние процессы.

## Установка

Единственная зависимость хоста — Docker. Ничего ставить в систему не нужно.

```bash
git clone https://github.com/I1eanch/kzru-ocr.git
cd kzru-ocr
docker build --target runtime -t kzru-ocr:latest -f docker/Dockerfile .
```

Сборка занимает 2–5 минут и требует доступа в интернет: скачиваются пакеты
Debian и языковые модели Tesseract. После сборки **интернет не нужен** —
модели лежат внутри образа.

Что зафиксировано в сборке, а что нет: базовый образ закреплён по digest,
версии Python-зависимостей — в `requirements.lock`, языковые модели
проверяются по sha256. **Не зафиксировано**: версии системных пакетов Debian
(`apt-get update` тянет текущее состояние репозитория bookworm) и хеши
колёс в lock-файле (`pip install` идёт без `--require-hashes`). Рецепт
полной герметичности — в [DEPLOY.md](docs/DEPLOY.md).

Если Docker-демон ограничен по ресурсам, сборке достаточно 2 ГБ памяти.

### Сборка за корпоративным прокси

```bash
docker build --target runtime -t kzru-ocr:latest -f docker/Dockerfile . \
  --build-arg HTTP_PROXY=$HTTP_PROXY --build-arg HTTPS_PROXY=$HTTPS_PROXY
```

### Опциональный образ с PaddleOCR

Нужен только для экспериментов со вторым движком, собирается на x86_64:

```bash
docker build --platform linux/amd64 --target full -t kzru-ocr:full -f docker/Dockerfile .
```

## Проверка установки

Три команды, которые должны отработать сразу после сборки.

```bash
# 1. Движок и языки на месте
docker run --rm kzru-ocr:latest sh -c 'tesseract --version | head -1; tesseract --list-langs'
```

Ожидается `tesseract 5.3.0` и языки `kaz`, `osd`, `rus`.

```bash
# 2. Готовность сервиса — fail-closed
docker run --rm kzru-ocr:latest python -c "
import service.app as a
ready, detail = a._readiness()
print('ready' if ready else 'NOT READY', detail['problems'])"
```

Ожидается `ready []`. Непустой список означает, что чего-то не хватает для
работы профиля по умолчанию, и сервис объявит себя неготовым на `/readyz`.

```bash
# 3. Дымовая проверка собранного образа целиком
scripts/smoke.sh kzru-ocr:latest
```

Проверяет состав образа, права пользователя, оба эндпоинта состояния,
контракт полей, границы входа, коды ответов и работу очереди заданий.
Завершается строкой `дымовая проверка пройдена`.

Логику критичных полей и бенчмарк проверяет dev-образ — см.
[Тестирование](#тестирование).

## Запуск: HTTP-сервис

Так модуль работает в эксплуатации. Пул рабочих процессов создаётся один раз
и переиспользуется между запросами, поэтому документ не платит заново за их
старт: замерено 2.97 с на холодном запросе против 2.42 с на последующих,
то есть 0.54 с экономии на документе.

Чего сервис **не** делает: модели Tesseract резидентными не становятся.
Распознавание идёт вызовом внешнего бинаря `tesseract`, который читает
`.traineddata` заново на каждый вызов; повторное чтение обслуживает страничный
кэш ОС, а не процесс сервиса.

```bash
docker run -d --name kzru-ocr --restart unless-stopped \
  -p 127.0.0.1:8099:8099 \
  --memory=4g --cpus=4 \
  --security-opt no-new-privileges \
  kzru-ocr:latest
```

Порт **привязан к loopback** сознательно: сервис не имеет аутентификации и не
должен быть доступен извне. Полный набор рекомендуемых флагов запуска — в
[docs/DEPLOY.md](docs/DEPLOY.md).

### Ограничение нагрузки

Сервис не позволяет запросам перегрузить хост. Все страницы всех запросов
идут через один пул процессов, размер которого равен доступным ядрам, а число
одновременно обрабатываемых документов ограничено отдельно. Настраивается
переменными окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `KZRU_PAGE_WORKERS` | доступные ядра | размер общего пула страничных воркеров |
| `KZRU_MAX_DOCUMENTS` | 2 | одновременно обрабатываемых документов |
| `KZRU_MAX_QUEUED_JOBS` | 8 | вместимость очереди фоновых заданий |
| `KZRU_JOB_TTL` | 900 | сколько секунд хранится готовый результат |
| `KZRU_SLOT_TIMEOUT` | 30 | сколько секунд запрос ждёт свободного слота |

При исчерпании слотов `/ocr` отвечает `503` с `Retry-After`, а `/jobs` —
`429`. Это сознательно: лучше отказать сразу, чем принять работу, которую
нечем выполнить.

### `GET /healthz` — живость

Отвечает `200` всегда, пока процесс жив. Внешних зависимостей не проверяет и
для решения «пускать ли трафик» не годится.

### `GET /readyz` — готовность

Проверяет то, без чего профиль по умолчанию не отработает: бинарь Tesseract,
его языковые модели, доступность PDF-бэкенда. Отвечает `200` при полной
готовности и **`503`** при любой проблеме, перечисляя её в поле `problems`.
Именно этот адрес используется в `HEALTHCHECK` образа и должен использоваться
балансировщиком.

```bash
curl -s localhost:8099/readyz | jq '{status, problems, profiles, limits}'
```

### `POST /ocr` — синхронное распознавание

Основной метод. Подходит для документов до ~10 страниц.

| Параметр | Где | Обязателен | Значения |
|---|---|---|---|
| `file` | multipart | да | PDF-файл |
| `profile` | query | нет | любой из `readyz.profiles`; по умолчанию `balanced` |
| `render` | query | нет | `default`, `cells`, `pipe`, `space`, `joined`, `no-headers`, `flat` |

```bash
curl -s -F file=@scan.pdf 'localhost:8099/ocr?profile=balanced' > result.json
```

### Фоновые задания

Для больших документов, чтобы PHP-воркер не висел на соединении.

| Метод | Назначение |
|---|---|
| `POST /jobs` | принять документ; `202` с `job_id` и `ttl_s` |
| `GET /jobs/{id}` | состояние: `running`, `done` (поле `result`), `failed` (поле `error`) |
| `GET /jobs/{id}?consume=1` | то же и сразу удалить результат |
| `DELETE /jobs/{id}` | удалить задание и его временные файлы |
| `GET /jobs` | сводка очереди: сколько заданий, сколько выполняется, вместимость |

```bash
JOB=$(curl -s -F file=@big.pdf 'localhost:8099/jobs' | jq -r .job_id)
curl -s "localhost:8099/jobs/$JOB?consume=1"
```

Готовый результат живёт `KZRU_JOB_TTL` секунд, после чего удаляется вместе с
временными файлами. Забирайте результат с `consume=1` либо удаляйте явно —
хранилище заданий держится в памяти процесса и намеренно ограничено.

### Коды ответов

| Код | Значение |
|---|---|
| `200` | успех |
| `202` | задание принято в очередь |
| `204` | задание удалено |
| `400` | неизвестный профиль, неизвестный профиль вывода или пустой файл |
| `404` | задание не найдено или устарело |
| `413` | файл больше 15 МБ; приём обрывается на лимите |
| `422` | больше 30 страниц или повреждённый PDF |
| `429` | очередь заданий заполнена |
| `503` | сервис не готов (`/readyz`) или нет свободных слотов обработки |
| `500` | внутренняя ошибка; в ответе только идентификатор, подробности в журнале |

## Запуск: командная строка

Удобно для разовой обработки и для проверки на своих документах.

```bash
# один файл, результат в stdout
docker run --rm -v "$PWD":/data -w /data kzru-ocr:latest \
  python -m ocr.cli /data/scan.pdf

# каталог, результат в .txt рядом, отчёт с предупреждениями в JSON
mkdir -p "$PWD/out"
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD":/data -w /data kzru-ocr:latest \
  python -m ocr.cli --in-dir /data/scans --out-dir /data/out --json /data/report.json
```

Про `--user`: контейнер работает от `uid=10001 (ocr)`, поэтому любой
смонтированный каталог, **в который** он пишет (`--out-dir`, отчёты,
результаты bench), должен быть доступен этому uid. На Linux без
`--user "$(id -u):$(id -g)"` запись упирается в `Permission denied`; на
macOS Docker Desktop это не проявляется, поэтому проблема легко ускользает
при локальной проверке. Альтернатива — заранее отдать каталог uid 10001:
`sudo chown -R 10001:10001 out`. Монтирование только для чтения
(`-v ...:/data:ro`) флага `--user` не требует.

Основные флаги:

| Флаг | Назначение |
|---|---|
| `--profile` | `fast` / `balanced` / `accurate` |
| `--render` | конвенция вывода, в том числе разделитель ячеек таблиц |
| `--workers` | число процессов; по умолчанию общий пул по доступным ядрам |
| `--no-text-layer` | игнорировать текстовый слой, всё гнать через OCR |
| `--json` | отчёт: поля, предупреждения, время, уверенность |
| `--pdf-backend` | растеризатор: `poppler` (по умолчанию). Значение `pymupdf` доступно только в dev-образе — в production PyMuPDF не поставляется |

## Интеграция с PHP / CodeIgniter 4

Готовый клиент — `php/OcrClient.php`. Скопируйте его в `app/Libraries/`.

```php
use App\Libraries\OcrClient;

$client = new OcrClient();              // или new OcrClient('http://127.0.0.1:8099')
$result = $client->recognize($pathToPdf, 'balanced');

$text   = $result['text'];
$fields = $result['fields'];

// Значения, пригодные для автоматического разбора: для БИН это статусы
// valid и repaired, для дат — только календарно валидные.
$bins  = OcrClient::confirmedValues($fields, 'bin');
$dates = OcrClient::confirmedValues($fields, 'dates');

// Всё, что требует человека: исправленные и непроверенные номера,
// несуществующие даты, суммы с расхождением прописи.
foreach (OcrClient::needsReview($fields) as $item) {
    // $item['field'] — bin | dates | amounts
    // $item['item']['raw'] — как это было прочитано
    $document->flagForManualReview($item);
}

foreach ($result['warnings'] as $w) {
    // $w['type'], $w['page'], $w['detail']
}
```

> [!WARNING]
> Не считайте `fields.bin` подтверждённым списком номеров. Запись со статусом
> `repaired` — это гипотеза, подобранная по контрольной сумме, а `unverified`
> проверку вовсе не прошла. Используйте `confirmedValues()` и
> `needsReview()`, а не перебор `fields['bin']` напрямую.

Адрес сервиса берётся из переменной окружения `OCR_SERVICE_URL`, по умолчанию
`http://127.0.0.1:8099`. Клиент сам делает повторы при сетевых сбоях и не
повторяет запрос при ошибках `4xx`. Таймаут по умолчанию 180 секунд —
увеличьте, если обрабатываете 30-страничные документы профилем `accurate`.

## Профили распознавания

| Профиль | Что делает | Когда применять |
|---|---|---|
| `fast` | 250 DPI, без выравнивания и бинаризации | предварительный просмотр, заведомо чистые сканы |
| `balanced` | 300 DPI, определение ориентации, выравнивание перекоса, бинаризация, уточняющий проход по числам | **по умолчанию**, основной режим |
| `accurate` | то же при 400 DPI | документы, где критичны числа |
| `ft-balanced`, `ft-accurate` | то же на дообученной модели `kzru_doc` | **экспериментальные**, см. ниже |

Профили `ft-*` работают на дообученной модели. Дефолтом она не является и по
итогам двух независимых замеров проигрывает stock: теряет один БИН из
шестнадцати и уступает по CER (0.0220 против 0.0190). Профили оставлены для
перепроверки на реальных сканах заказчика — там расклад может отличаться.
Подробности в [инженерных записках](docs/ENGINEERING.md).

Профиль вывода (`render`) управляет только оформлением текста и не влияет на
распознавание:

| Профиль вывода | Таблицы | Прочее |
|---|---|---|
| `default` | ячейки через табуляцию | — |
| `cells` | каждая ячейка с новой строки | — |
| `pipe` | ячейки через ` \| ` | — |
| `space` | ячейки через два пробела | — |
| `joined` | как `default` | склеивает слова, разорванные переносом |
| `no-headers` | как `default` | убирает колонтитулы и номера страниц |
| `flat` | ячейки через пробел | всё вышеперечисленное сразу |

Если у вас есть эталонные тексты в своей конвенции (каталоги `scans/` и
`gt/` в текущей директории), подходящий профиль подбирается замером, а не
на глаз:

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD":/data -e OUT_DIR=/data/grid \
  kzru-ocr:dev sh /app/bench/grid.sh /data/scans /data/gt balanced
```

Скрипт прогоняет все профили вывода и печатает CER/WER по каждому. Он живёт
только в образе `dev` — в `runtime` каталога `bench` нет. Промежуточные
файлы (`pred_*`, `grid_*.json`) пишутся в `OUT_DIR`: по умолчанию это
`bench/` рядом со скриптом, что в контейнере недоступно на запись
(каталог принадлежит root, процесс — uid 10001), поэтому `OUT_DIR` обязателен.
Здесь он указывает в смонтированный `/data`, и результаты остаются у вас
в `./grid/`; если файлы не нужны, подойдёт и `-e OUT_DIR=/tmp/grid` —
тогда `--user` можно опустить.

## Формат вывода и предупреждения

`POST /ocr` возвращает JSON:

```json
{
  "file": "scan.pdf",
  "profile": "balanced",
  "elapsed_s": 2.9,
  "mean_conf": 0.93,
  "text": "ДОГОВОР № 864 купли-продажи\n...",
  "pages": [
    {"index": 0, "source": "ocr", "engine": "tesseract",
     "rotation": 0, "skew": -1.1, "dpi": 300, "mean_conf": 0.93}
  ],
  "fields": {
    "bin": [
      {"value": "184959310345", "raw": "184959310345", "status": "valid",
       "candidates": ["184959310345"], "requires_review": false},
      {"value": "751079911835", "raw": "751079911834", "status": "repaired",
       "candidates": ["751079911835"], "requires_review": true}
    ],
    "amounts": [
      {"value": "750000", "raw": "750 000 (семьсот пятьдесят тысяч)", "words_match": true}
    ],
    "dates": [
      {"value": "2020-09-15", "raw": "15.09.2020", "status": "valid"}
    ]
  },
  "warnings": [
    {"type": "text_layer_rejected", "page": 0, "detail": "слой пуст или почти пуст"}
  ]
}
```

Поле `source` у страницы показывает, откуда взят текст: `text_layer` — из
текстового слоя PDF, `ocr` — распознан.

### Статусы полей

Каждое значение несёт собственный статус проверки. Плоский список строк
здесь был бы обманом: номер, прошедший контрольную сумму как прочитан, и
номер, подобранный перебором, выглядели бы одинаково.

| Поле | Признак | Значения |
|---|---|---|
| `bin` | `status` | `valid` — контрольный разряд сошёлся; `repaired` — номер исправлен, кандидат был ровно один; `unverified` — проверка не пройдена, `value` равен прочитанному и подтверждением не является |
| `bin` | `requires_review` | истинно для всего, кроме `valid` |
| `bin` | `candidates` | валидные кандидаты, найденные перебором |
| `dates` | `status` | `valid` (`value` в ISO) либо `invalid` (`value` равен `null`) |
| `amounts` | `words_match` | `true` — совпало с суммой прописью; `false` — расхождение; `null` — прописи рядом не было |

### Предупреждения

Это рабочий инструмент, а не отладочный вывод: по ним принимается решение,
отправлять ли документ на ручную проверку.

| Тип | Значение | Что делать |
|---|---|---|
| `bin_checksum_failed` | номер не проходит контрольную сумму и не исправим | проверить вручную |
| `bin_repaired` | номер **исправлен** по контрольной сумме | сверить с оригиналом |
| `bin_ambiguous_fix` | исправлений несколько, ни одно не выбрано | проверить вручную |
| `amount_mismatch` | сумма цифрами не совпадает с прописью | проверить вручную |
| `date_invalid` | несуществующая дата | проверить вручную |
| `low_confidence_page` | средняя уверенность страницы ниже 0.70 | скорее всего плохой скан |
| `text_layer_rejected` | текстовый слой признан негодным, страница распознана | информационное |
| `engine_disagreement` | движки разошлись в цифрах | проверить вручную |
| `page_failed` | страница не обработана | технический сбой |

Рекомендуемое правило для сервиса проверки документов: любое предупреждение
семейства `bin_*` и `amount_mismatch` — повод показать документ оператору.

## Тестирование

Тесты и бенчмарк живут в **dev-образе**: в production-образ не входят ни они,
ни их зависимости. Соберите его один раз:

```bash
docker build --target dev -t kzru-ocr:dev -f docker/Dockerfile .
```

### 1. Логика критичных полей

```bash
docker run --rm kzru-ocr:dev python tests_domain.py
```

Покрывает контрольный разряд БИН/ИИН (обе серии весов и известное слепое
пятно 11-й позиции), разбор русских и казахских числительных, календарь,
нормализацию похожих символов, а также статусы полей: непрошедший проверку
номер обязан остаться видимым, но неподтверждённым.

### 2. Поведение HTTP-слоя

```bash
docker run --rm kzru-ocr:dev python -m pytest tests_service.py -v
```

Каждый тест защищает конкретный отказ: обрыв приёма файла на лимите,
отсутствие утечки файловых дескрипторов, fail-closed готовность, ограниченная
очередь заданий, удаление результатов по TTL, `422` на повреждённом PDF,
совпадение рекламируемых и принимаемых профилей, отсутствие внутренних
подробностей в ответе об ошибке.

### 3. Дымовая проверка production-образа

```bash
scripts/smoke.sh kzru-ocr:latest
```

Проверяет собранный образ снаружи: что в нём нет dev-зависимостей и каталога
`bench`, что процесс идёт не от root, что liveness и readiness разведены, что
границы входа и коды ответов соответствуют документации.

### 4. Бенчмарк на синтетическом наборе

Модуль умеет сам породить себе тестовые данные — реальные документы для этого
не нужны:

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD":/data -w /app kzru-ocr:dev sh -c '
  python -m bench.make_sample_docs --out-dir /data/bench/data --count 8 --seed 42
  python -m bench.make_pseudoscan --src-dir /data/bench/data \
      --out-dir /data/bench/scans --gt-dir /data/bench/gt \
      --dpi 200 --degrade medium --seed 42
  python -m ocr.cli --in-dir /data/bench/scans --out-dir /data/bench/pred
  python -m bench.run_bench --pred-dir /data/bench/pred --gt-dir /data/bench/gt \
      --csv /data/bench/report.csv --worst 5'
```

`make_sample_docs` создаёт уставы, договоры и справки с **валидными по
контрольной сумме** БИН и ИИН, казахскими абзацами и таблицами, а рядом с
каждым PDF кладёт `<name>.fields.json` — независимый эталон полей, взятый из
переменных генератора, а не из разбора готового текста. `make_pseudoscan`
превращает документы в сканы с перекосом, шумом и JPEG-артефактами и
переносит этот эталон дальше. Всё детерминировано по `--seed`.

Уровни ухудшения: `light`, `medium`, `heavy`.

> [!IMPORTANT]
> Если рядом с эталонным текстом нет `.fields.json`, `run_bench` разбирает
> эталон тем же экстрактором, что и предсказание, и честно предупреждает, что
> оценка циклична. Разница не теоретическая: на одном и том же наборе
> циклическая оценка показывала `amounts exact 1.0` ещё тогда, когда
> экстрактор вовсе не видел суммы, разорванные переносом строки — дефект
> маскировался с обеих сторон. Независимый замер по `.fields.json` вскрыл
> это как `0.6667`; после исправления экстрактора независимый замер даёт
> `1.0000`.

### 5. Бенчмарк на ваших документах

Главный сценарий приёмки. Нужны два каталога: сканы и эталонные тексты с
теми же именами файлов.

```
your-data/
  scans/  doc_001.pdf  doc_002.pdf ...
  gt/     doc_001.txt  doc_002.txt ...
```

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v /path/to/your-data:/data -w /app kzru-ocr:dev sh -c '
  python -m ocr.cli --in-dir /data/scans --out-dir /data/pred --profile balanced
  python -m bench.run_bench --pred-dir /data/pred --gt-dir /data/gt \
      --csv /data/report.csv --json /data/report.json --worst 10'
```

Вывод содержит:

- **CER и WER в двух режимах** — `strict` (посимвольно как есть) и
  `normalized` (единый регистр, схлопнутые пробелы, унифицированные тире и
  кавычки). Два режима даются потому, что конвенция подсчёта у сторон может
  отличаться, и подменять одну другой некорректно.
- **Два вида усреднения** — микро (взвешенно по символам эталона) и макро
  (среднее по документам). Это разные числа, оба печатаются.
- **Field-accuracy** — precision, recall и exact match отдельно по `bin`,
  `amounts`, `dates`.
- **`--worst N`** — худшие документы с первой расходящейся строкой, чтобы
  сразу видеть характер ошибок.
- **`--csv` и `--json`** — построчный отчёт для дальнейшего анализа.

Документ, для которого нет результата распознавания, считается ошибкой с
CER = 1.0 и помечается `MISSING` — он не пропускается молча.

### 6. Сравнение конфигураций

Если нужно выбрать движок или параметры под ваши документы:

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v /path/to/your-data:/data -w /app kzru-ocr:dev \
  python -m bench.bakeoff --scans /data/scans --gt /data/gt --only tesseract
```

Печатает таблицу: CER, **отдельную ошибку по цифрам** и секунды на страницу
для каждой конфигурации. Ошибка по цифрам считается отдельно сознательно: в
общем CER цифры растворяются, и конфигурация с худшим CER может оказаться
лучшей на числах.

### 7. Замер производительности

```bash
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD":/data -w /app kzru-ocr:dev \
  python -m bench.measure_parallel --pdf /data/bench/scans/doc_001_dogovor.pdf --repeat 8
```

Печатает время и ускорение при разном числе процессов.

## Производительность

Замеры на 4-ядерном x86_64 VPS (Debian 12, Docker, `--cpus` не ограничен),
профиль `balanced`, документ из 8 одинаковых страниц A4, скрипт
`bench/measure_parallel.py`:

| Процессов | Итого | На страницу | Ускорение |
|---|---|---|---|
| 1 | 20.5 с | 2.56 с | 1.00× |
| 2 | 12.6 с | 1.57 с | 1.62× |
| 4 | 6.5 с | 0.82 с | 3.13× |

> [!NOTE]
> В [инженерных записках](docs/ENGINEERING.md) для 4 процессов указано
> 9.3 с и 2.19×. Это **другой замер**, а не опечатка: он снят до перевода

> конкурирует с воркерами за потоки внутри интерпретатора, и ускорение
> выросло с 2.19× до 3.13×. Таблица выше — актуальная; условия и происхождение
> обеих зафиксированы в записках.

Ориентиры по документам:

| Сценарий | Время |
|---|---|
| Страница с пригодным текстовым слоем | ~7 мс |
| Страница, профиль `fast` | ~1.9 с |
| Страница, профиль `balanced` | ~2.5 с на ядро |
| **Документ 30 страниц, `fast`, 4 ядра** | **10.5 с** (замерено) |
| Документ 30 страниц, `balanced`, 4 ядра | ~25 с (пересчёт из 0.82 с/стр, отдельно не замерялось) |

Качество на синтетическом наборе (8 документов, 16 769 символов эталона,
псевдосканы 200 DPI, ухудшение `medium`), профиль `balanced`, вывод `cells`:

| Метрика | Значение |
|---|---|
| CER `strict` | 0.0351 |
| CER `normalized` | **0.0191** |
| WER `normalized` | 0.0476 |
| БИН: precision / recall / exact | 1.0000 / 1.0000 / 1.0000 (независимый эталон) |
| Суммы: exact | 1.0000 (независимый эталон) |
| Даты: exact | 1.0000 (независимый эталон) |

> [!NOTE]
> Раньше в этой таблице стояло 1.0000 по всем трём полям — это была
> **циклическая оценка**: эталон разбирался тем же экстрактором, что и

таблиц: `cells` даёт 0.0191, `default` — 0.0244, `pipe` — 0.0348. Если у вас
есть эталоны, [подберите профиль замером](#профили-распознавания).

На сканах 150 DPI — нижней границе из требований — качество не падает.

> Эти цифры получены на синтетических документах с чистыми гарнитурами.
> На реальных сканах их нужно перепроверить — для этого и существует
> [бенчмарк на ваших документах](#5-бенчмарк-на-ваших-документах).

## Ограничения

Честный список того, что модуль делает плохо или не делает.

- **Сильно испорченные сканы.** При ухудшении уровня `heavy` (перекос до
  ±2.5°, соль-перец, JPEG q35) CER поднимается до 38%, суммы перестают
  извлекаться. Модуль это **видит**: уверенность падает до 0.5, число
  предупреждений утраивается — такой документ следует отправлять оператору.
- **Ложные 12-значные последовательности.** На плохих сканах регулярное
  выражение может зацепить мусор. Контрольная сумма отсеивает почти всё, но
  случайная последовательность проходит её примерно в одном случае из
  одиннадцати.
- **Слияние колонок таблицы**, если значение в итоговой строке сдвинуто.
  Текст не теряется — страдает только расстановка разделителей ячеек.
- **Склейка числа, разорванного переносом внутри разрядов, требует прописи.**
  Запись «3 700\n000 (три миллиона семьсот тысяч) тенге» собирается верно,
  потому что пропись подтверждает результат. Без прописи — «500\n000 тенге» в
  колонке таблицы — склейка сознательно не выполняется: соседние строки дали
  бы несуществующую сумму. Такая величина в поля не попадёт.
- **Цветные печати не удаляются.** Текст под печатью может портиться.
- **Рукописный текст не поддерживается** — модуль рассчитан на машинный шрифт.
- **Асинхронные задачи хранятся в памяти процесса**: перезапуск сервиса
  теряет ещё не забранные результаты. Горизонтальное масштабирование сервиса
  потребует внешнего хранилища заданий.
- **Нет аутентификации.** Сервис рассчитан на loopback; не публикуйте порт.
- **Все замеры сделаны на синтетическом наборе** с гарнитурами DejaVu. На
  реальных сканах их нужно перепроверить; для этого есть `bench/run_bench.py`
  и `bench/bakeoff.py`.

## Лицензии

| Компонент | Лицензия | Где |
|---|---|---|
| Tesseract, языковые модели | Apache-2.0 | production |
| poppler-utils | GPL-2 | production, вызывается как внешний процесс, без линковки |
| OpenCV headless, NumPy, FastAPI, pytesseract, RapidFuzz | Apache-2.0 / BSD / MIT | production |
| jiwer, pytest, httpx | Apache-2.0 / MIT / BSD | только dev-образ |
| PyMuPDF | **AGPL-3.0** | только dev-образ, в production-образ не копируется |
| PaddleOCR, PaddlePaddle | Apache-2.0 | только образ `full`, по умолчанию отключён |

Состав production-образа проверяется автоматически: `scripts/smoke.sh`
падает, если в нём обнаружатся PyMuPDF, jiwer, pytest или каталог `bench`.
Это констатация состава поставки, а не юридическое заключение о применимости
лицензий к вашему продукту.
